§04Accessibility contract

Color is a hint, never the signal.

Every state that matters to a decision — sealed vs. open, mapped vs. unmapped, error vs. success — carries a second, non-color channel: shape, glyph, or text. This is the fix for the finding that the gate-seal used color alone.

Don't

  • Signal "sealed" with fill color alone on an unlabeled circle.
  • Rely on the ember/brass hue difference — indistinguishable for red-green colorblind users at this saturation.
  • Ship a focus state only on inputs; buttons and tabs need one too.

Do

  • Pair color with a shape change (hollow ring → solid disc + ✓ glyph) and a visually-hidden label.
  • Use --focus-ring on every interactive element via :focus-visible.
  • Real <button>/<select> elements with associated <label>s — never a styled <div> with an onclick.

Gate-seal — before / after

Complete Sealed — shape (disc + check) AND color, not color alone
Incomplete Open — hollow ring, distinct silhouette even in grayscale

§07Form states & validation

Every field, every state, in plain language.

The Build form and Publish steps are where a volunteer admin does the most typing. Validation is immediate — on blur, not on submit — so a mistake gets caught before it's forgotten. Every error names what's wrong and what to do about it; never a bare "Invalid input."

States — real DragonGate fields

Unpublish the portal to change where responses are saved.

That doesn't look like a Sheet ID — paste the long code between /d/ and /edit in the sheet's URL, not the whole link.

Connected — DragonGate can write submissions here.

Unmapped-field warning — Build form → Map data step

A field the admin added to the form but never assigned to a Sheet column. This blocks Publish — the warning says which field, and the fix is one click away, not a hunt through the form.

Don't

"Validation error: field mapping incomplete."

Do

"'Organization budget' isn't going anywhere yet — pick a Sheet column for it before you publish."

§08Empty states

Nothing here yet is not the same as broken.

A first-run admin sees an empty dashboard before they see a single portal. The empty state has to do the job a demo video usually does: say what's missing, and hand over the one next action.

No portals yet — main dashboard

No portals yet

Create your first portal to start collecting applications — a grant, a prize, a scholarship. Takes about five minutes.

No saved templates — template picker

No templates saved

Save any portal as a template to reuse its form and field mapping next cycle. You haven't saved one yet.

Don't

  • Show a blank table with no explanation.
  • Lead with an illustration and bury the CTA below the fold.

Do

  • Name what's missing in plain words, then one clear next step.
  • Reuse the same button and gate-seal glyphs the rest of the product already uses — the empty state isn't a special skin.
§09Loading & saving states

The admin should never wonder if the click landed.

"Update portal" writes to the database and, when connected, to the Google Sheet — two round-trips that can each take a second or two. The button shows its own state; nothing else on the page should require a guess.

Update-portal flow — button carries the state

Idle — ready to save
In flight — label changes tense, spinner is the second signal (never color alone)
Confirmed — reverts to "Update portal" after 2s, or on next edit

List loading — portal dashboard skeleton

Skeletons, not spinners, for lists — the shape of the eventual content is already visible, which reads as "almost there" instead of "unknown wait." A spinner is reserved for a single in-flight action tied to one button.

§12Voice & tone

Written for a volunteer, not a developer.

The person configuring a DragonGate portal is usually a nonprofit volunteer or part-time program admin — not a WordPress developer, not an engineer. Copy assumes no technical background, names concrete next actions, and never blames the admin for a mistake the system could have prevented.

Button labels — active voice, named object

Don't

  • "Submit"
  • "OK"
  • "Save Changes"

Do

  • "Publish portal"
  • "Connect this Sheet"
  • "Update portal"

Errors — plain language, always a fix

Don't

  • "Error: 403 Forbidden."
  • "Invalid Sheet ID."

Do

  • "DragonGate can't write to that sheet — make sure it's shared with dragongate@yourdomain.iam.gserviceaccount.com."
  • "That doesn't look like a Sheet ID — paste the code between /d/ and /edit in the sheet's URL."

Empty states — name it, hand over the next step

"No portals yet. Create your first portal to start collecting applications." — never "No data found."

Confirmations — past tense, no exclamation marks

"Portal published. Applicants can now submit at the link below." — not "Success!! Your portal is live!!"

Tone by surface

SurfaceTone
Start / template pickerWarm, encouraging — this is the admin's first impression of the plugin.
Build form / Map dataPrecise, procedural — the admin is doing careful configuration work; don't editorialize.
Errors anywhereCalm and specific. Never "Oops!" — name the problem and the fix in one sentence.
Publish confirmationQuietly confident. The gate is sealed; say so plainly.
§13Accessibility checklist

Verified pairs, not assumed ones.

Every ratio below is computed from the hex values in :root above, not eyeballed. Two pairs fail AA for normal text and are flagged with their actual required use — this is the honest state of the palette, not a claim that everything passes.

PairRatioVerdict
--ink on --paper16.9 : 1AA + AAA, any text size.
--ink-600 on --paper8.3 : 1AA + AAA, any text size. Body copy default.
--ink-400 on --paper4.4 : 1Fails AA for normal text (needs 4.5). Passes for large text (≥18px / 14px bold) and icons only — use for captions/help text at ≥13px with generous line-height, never for small critical copy.
--ember-600 on --paper6.3 : 1AA + AAA. Link color, safe at body size.
white on --ember5.0 : 1AA for normal text. Primary button label.
--error on --paper5.4 : 1AA. Safe for error text at body size.
--success on --paper3.8 : 1Fails AA for normal text. Use only for large text, icons, or paired with a bold weight — the "Saved" confirmation in §09 uses it on a filled button (white-on-color contrast, not text-on-paper), which is the safe pattern.
--brass on --paper3.6 : 1Fails AA for normal text. Reserved for eyebrow labels (which are decorative/redundant with adjacent headings) and icon strokes — never load-bearing body copy.

Keyboard navigation

  • Tab order through Build form follows visual order top-to-bottom, left-to-right; the Map data table is tabbable row by row, each Sheet-column select reachable without a mouse.
  • Every actionable element (button, select, gate-seal-triggering control) is a real focusable element with --focus-ring visible on :focus-visible — never suppressed with outline: none alone.
  • The Publish confirmation and any destructive action (delete portal, unpublish) is reachable and confirmable via keyboard alone, with focus returned to a sensible element after the action completes.

Screen-reader labels

  • The gate-seal never relies on its shape or color alone — every instance carries a <span class="sr-only"> announcing "Complete" or "Incomplete" (see §04, §11).
  • Icon-only buttons (a trash icon to remove a mapped field, a gear to open portal settings) carry an aria-label naming the action and its target — "Remove Organization budget field," not "Remove."
  • The saving spinner (§09) sits in an aria-live="polite" region so a screen-reader user hears "Saving…" then "Saved" without needing to poll the button.

Touch targets & motion

  • Every button and gate-seal-triggering control is at least 40px on the shortest side inside wp-admin's own touch-friendly chrome.
  • All shimmer/spin animations (§09) respect prefers-reduced-motion — spinners slow to a calmer pace, skeleton shimmer becomes a flat tone. Neither loses its meaning when motion is reduced.
§14Responsive behavior

This is wp-admin. Its collapse rules already exist — don't fight them.

DragonGate renders inside the WordPress admin shell, which already owns responsive behavior for the sidebar and top toolbar. The plugin's job is to make sure its own screens (Build form, Map data table, Publish) degrade cleanly inside whatever width wp-admin gives them — not to invent a parallel breakpoint system.

Widthwp-admin doesDragonGate does
> 960pxFull sidebar, expanded menu labels.Two-column form layouts (as in §07); mapping table shows all columns side by side.
782–960pxSidebar auto-folds to icons-only (the native "folded" admin menu).No change needed — DragonGate's content area simply gets narrower; two-column field groups already wrap via existing grid, no override required.
< 782pxwp-admin switches to its mobile nav (hamburger toggle, sidebar becomes an overlay).Field-mapping table (§10) stacks to one row per field, label above value; template gallery cards drop to a single column; button rows go full-width and stack vertically.

Deliberately no dark mode: DragonGate is a light-only surface, matching the parchment-and-ember palette established in §01 — wp-admin's own dark "Midnight" color scheme wraps our screens without inverting them, the same way any other plugin's light-surface settings page coexists inside a dark admin theme today.

§15Implementation note

Where this lives in code.

These tokens map 1:1 onto a tailwind.config.js theme.extend block consumed by the existing Svelte app (src/ → assets/dist/dragongate-portal.js). No new framework, no new build tool — the gate-seal, button, field-mapping, form-field, empty-state, and skeleton components above become Svelte components with data-state props driving the exact CSS shown here.
